# Publishing checklist and honest post templates

Use this after real work exists. These are drafts; no post, application, issue or message is sent by using this toolkit.

## Before publishing

- [ ] The project status and my contribution are accurate.
- [ ] Every numerical claim links to an actual result with protocol, sample size and denominator/context.
- [ ] Baseline and candidate used a fair common evaluation set.
- [ ] Demo output is labeled live, precomputed, simulated or historical as appropriate.
- [ ] The README has a working small run, an evaluation link, and limitations.
- [ ] I tested the documented setup in a fresh environment.
- [ ] I can explain the important code and repair a small unfamiliar failure.
- [ ] No API keys, personal application notes, private examples or unlicensed materials are included.
- [ ] Code/data/documentation/model licenses and credits are separate and accurate.
- [ ] Images/video are readable; captions or a written equivalent convey the same result.
- [ ] “Submitted,” “reviewed,” and “merged” match the actual contribution state.
- [ ] Unfilled placeholders, invented impact and unsupported “production scale” claims are removed.

## Profile placement

Pin the strongest completed, role-relevant flagship first, then the complementary flagship. Link the reliability release within its project. A documentation or learning application you have actually built can provide supporting evidence of interface/documentation/delivery work. Fewer strong pins are fine; six is a platform maximum, not a goal.

Use LinkedIn Featured for a real case study, a short demonstration, and a portfolio overview when available. Label independent projects accurately. Early-stage headline example: “Learning Python and ML engineering through reproducible projects.” Change it only as your actual evidence changes; a target role is not current employment.

## A 60–90-second demo

1. 0–10 seconds: show the user problem and one input.
2. 10–30 seconds: show actual useful behavior, with evidence/citations or a forecast origin.
3. 30–50 seconds: show a realistic failure and bounded response.
4. 50–70 seconds: show the baseline/evaluation comparison and sample size.
5. 70–90 seconds: state one tradeoff, your contribution, and where to reproduce it.

Do not hide failures with editing or imply a cached response was generated live. A written walkthrough can replace video.

## Post 1 — experiment and tradeoff

> I am building [tool] for [specific task]. I compared [baseline] with [candidate] on [N held-out units and split]. The measured [metric] was [A] versus [B], with [measured tradeoff]. The largest observed failure category was [category/example]. Here are the protocol, actual outputs and code: [link]. My next experiment asks [one question].

If no measurement exists, publish a smaller honest update about the implemented behavior and planned evaluation; remove all result wording. If the baseline wins, say so.

## Post 2 — failure and repair

> This [non-private input] broke my [system]. I had assumed [assumption]. The [trace/test/data slice] showed [actual cause]. I changed [specific behavior] and added [regression check]. It still struggles with [remaining limit]. Before/after evidence and reproduction: [link].

## Post 3 — release and feedback

> I released [version] to test [specific need]. [Actual number/type] of testers tried [task]. I observed [specific finding] and changed [behavior]. This was [small formative test / controlled drill / historical replay]. The demo, evaluation, known limits and my contribution are here: [link]. I would value feedback on [specific design question].

If nobody has tried it, say “I have not tested this with users yet” and invite feedback without inventing adoption. Report a controlled drill as such.

## A sustainable review

Budget roughly 2–3 hours of the 36-hour study week for communication once artifacts exist. Publish after a useful experiment, fix or release, perhaps weekly or fortnightly; this is a planning heuristic, not a platform-ranking claim. Track reproducibility feedback, code review, qualified conversations and application stages. Stars and views do not certify engineering skill.
